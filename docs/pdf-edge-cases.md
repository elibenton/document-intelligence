**Method.** 34 PDF variants, one representative file per axis, each generated by
`scripts/make-variants.ts` and re-opened with pdf.js before use, then sent through
`npm run bench -- --variant=task-ocr`. Raw responses are in
`test-corpus/results/raw/`; `npx tsx scripts/summarize-variants.ts` rebuilds the
table below offline for free. Total spend for the whole matrix was about $0.60.

## 1. The finding that explains the failing document

**Interfaze does not OCR images inside a PDF. It reads the embedded text layer
and nothing else.**

This was not the working hypothesis, and the evidence for it is unambiguous:

| Experiment | Result |
|---|---|
| Same generator, page of painted text | **100% text**, perfect fidelity |
| Same generator, page of scanned pixels, no text layer | **empty** |
| Two-page file: page 1 a scan, page 2 painted text | **only page 2 came back** |
| The scan re-encoded five different ways | **empty every time** |

The encoding axis is flat. CCITT G4, JPEG, Flate grey, Flate bilevel, RGB, CMYK,
indexed and image masks all return empty alike. **Encoding was never the
variable** — which retires the CCITT hypothesis for a different reason than the
earlier rebuild experiment suggested.

### The earlier rebuild experiment was confounded

The conclusion "CCITT is not the cause, because rasterizing to JPEG did not help"
rested on `pdfFromJpegPages`, a writer that had never itself been checked against
the provider. Running it on a **known-good** document produced an empty response
too (`control-rebuild-working-p1`). The rebuild was not a control; it was a second
instance of the same failure, because rasterizing a document strips its text
layer. The conclusion happened to be right, for the wrong reason.

### It is occlusion, not merely absence

A page can have a perfectly good text layer and still return nothing:

| Page layout | Result |
|---|---|
| Text only | 100% |
| Text + small image in the corner (~7% of the page) | 100% |
| Text + image covering the bottom half, clear of the text | 100% |
| Text + full-page image drawn over it | **empty** |
| Text drawn in rendering mode 3 (invisible) | **empty** |

So the rule is: text that is invisible, or that a page-sized image covers, is
discarded. That is precisely the shape of every "searchable PDF" a scanner
produces — the OCR text is invisible, under the scan — which means the most
common scanned-document format in the world returns nothing from this provider.

### Scale

| Variant | OCR | Preflight now |
|---|---|---|
| 1 page | works | — |
| 45 pages | **45/45** complete | — |
| 60 pages | **50/60** — silently truncated | warn `page_limit_truncation` |
| 150 pages | **50/150** | warn `page_limit_truncation` |
| 520 pages | **50/520** | warn `page_limit_truncation` |
| 21 MB, 6 pages | blocked before sending — **never actually measured** | now sent, as a URL in prompt text |

**There is a hard 50-page ceiling.** 45 pages came back whole; 60, 150 and 520 all
returned exactly 50 pages, identical byte-for-byte in length and token count, with
no error and no indication of truncation. Page count and byte size are genuinely
independent: a 0.4 MB file can lose 470 pages while a 21 MB file of 6 pages was
refused outright.

**The byte ceiling was never a measurement.** The 21 MB row is the one line in
this table that reports our own gate rather than the provider's behaviour — the
file was blocked client-side and never sent, so nothing here says what Interfaze
does past 20 MB. The limit is documented per *transport*
(https://interfaze.ai/docs/limits): 20 MB for a file object, 80 MB for a URL in
prompt text. The upload gate is now the 80 MB one, and `fileUrlContent` switches
transport rather than refusing the document. What remains unmeasured is whether
the 20 MB file-object cap applies at all to a URL this SDK passes through
verbatim without inlining bytes — if it does not, the switch is unnecessary
caution costing ~11x on files above 19 MB.

## 3. Why nothing is repaired locally

The brief asked for repair where repair helps. It does not help here, and this was
tested rather than assumed.

The only defect worth repairing is the missing/unreadable text layer, since that
is what every failure reduces to. Two repairs were considered:

1. **Re-encode the images.** Refuted directly by the encoding axis — all five
   encodings fail identically. Re-encoding produces the same empty response more
   slowly.
2. **Recover the hidden text and re-emit it visibly.** Built and tested
   (formerly `scripts/lib/textUnderlay.ts`, deleted — recoverable from git
   history): rasterize each page, extract the invisible text with pdf.js, and
   rebuild with the text painted in mode 0 underneath the raster.
   **It failed against a real OCR call** — the page-sized raster covers the text,
   and covered text is discarded exactly as mode-3 text is.

Drawing the recovered text *on top* of the raster at zero alpha was the obvious
next attempt and was never tested against the provider. Since the genuine fix is
server-side (below), the harness was retired rather than carried indefinitely.

The genuine fix is not client-side at all: the per-page image path already works
(the failing document returns 17/17 clean pages when its pages are sent as PNGs).
Routing image-only PDFs through that path is a server change in
`convex/processingNode.ts`, which belongs to another session.

So preflight **detects and explains**, and does not re-encode. A user learns
before paying that their scan will come back empty, and what to do about it.

## 4. What preflight does now

`src/lib/pdfPreflight.ts` returns the same discriminated union, extended:

**Rejections** (`ok: false`, upload stops) — `empty`, `invalid_pdf`,
`password_protected`, `provider_size_limit`, and two new ones:
`permissions_restricted` and `oversized_pages`.

**Warnings** (`ok: true`, upload proceeds, message shown in the drop zone) —
`no_text_layer`, `page_limit_truncation`, `large_pages`, `form_fields_ignored`.

`annotations_ignored` was cut. The measurement behind it stands — a free-text
annotation really is dropped — but it bought a `getAnnotations()` call on every
sampled page of every upload to tell users that sticky notes are not part of the
document text, which is what most of them already assume. A warning has to change
what someone does, and that one didn't.

`no_text_layer` is a warning rather than a rejection on purpose: scanned documents
are the product's core use case, page rasterization and the viewer still work on
them, and `ocrDocument` already classifies the eventual failure as
`empty_ocr_response`. Blocking the upload would remove the user's choice; warning
makes the later failure interpretable, which is what it was missing.
